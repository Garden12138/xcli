**五、统一结果与任务记录契约**

以下字段是拟议语义，最终名称在阶段 0 冻结。先写兼容性样例，再修改各入口，避免前台、后台和恢复各自形成一套结果。

| 维度 | 设计约束 | 兼容方式 |
| --- | --- | --- |
| 任务身份 | 记录继续使用 `id`；规范化结果新增 `run_id`，关联 parent、step、attempt；每次执行有独立身份 | 保留旧 ID、旧读取路径和已有 `resumed_from`/`resumed_step` |
| 执行结果 | `exit_code` 保留原生进程退出码语义；增加 xcli 错误分类；区分取消、超时、启动失败 | 不用解析错误改写原生退出码；xcli 自身退出状态另行按规则计算 |
| 解析完整性 | `parse_status` 拟为 `complete`、`parse_error`、`truncated`、`not_applicable`、`unknown`；保留脱敏错误位置 | 旧记录缺字段读作 unknown；generic 文本模式为 not_applicable |
| 验证状态 | `not_run`、`passed`、`failed`、`inconclusive`，记录实际 command、cwd、时间与证据引用 | 历史 success 不自动升级为 passed；普通命令成功也不自动认定为测试通过 |
| 接收状态 | 默认未接收；只根据用户的明确接收动作记录 | 不从退出码、Git 提交存在或 Agent 自述推导 accepted |
| 目录与工作区 | workflow 与每一步保存实际 cwd；worktree 记录仓库、基线 commit、路径、分支 | 保留现有字段，缺失信息按明确的回退规则读取 |
| 用量 | 每次 attempt 保留可用 usage，再按逻辑步骤汇总；缺失值保持缺失 | 交互/ACP 的统计边界不变，缺失费用不当成 0 |
| 能力与来源 | 记录实际 CLI 版本、适配器和能力检测来源 | 无法检测时标记 unknown，不能用静态声明冒充验证 |

状态判定顺序建议为：启动失败/取消/超时优先；否则保留原生非零退出；原生退出 0 但结构化协议失败时，整体执行标为 failed，xcli 默认退出 1，并保存原生 `exit_code: 0` 和解析原因。各入口使用同一判定函数。未知事件类型可以按适配器规则忽略；非法数据、明确失败事件和必须完成信号缺失不能静默忽略。

保持现有 `--json` 单对象输出契约；后台 `--detach --json` 继续返回初始 Job，而不是最终结果。`runs show` 现有 JSON 默认行为保留，人类摘要通过新增选项提供。新增字段尽量可选，格式不兼容时显式升级 schema，提供旧样本的读取验证与降级限制说明。

**六、执行反馈与资源使用优化**

将适配器事件解析从通用启发式中拆出，复用现有 Agent registry 和进程管理。数据流为：原生 stdout → 适配器增量解析 → 统一事件 → 终端进度/后台日志/最终结果。无需引入守护进程或新的常驻服务。

1. 普通文本模式继续把最终回答写 stdout，活动与摘要写 stderr；用户启用明确的事件选项后，stdout 才输出 JSONL。交互 `use` 与 ACP 保持原生透传路径。
2. 事件至少包含版本、run ID、时间、类型，以及适用的 step/attempt。首批支持 started、progress、completed、failed；waiting 只在下游提供可验证信号时展示，长时间无输出显示“暂无新活动”。
3. 解析缓冲、尾部诊断、事件队列和最终输出各设上限。缓冲饱和可合并重复进度，但不能丢失完成、失败或用量事件；不得因终端消费慢而无限占用内存。
4. 已有完整输出记录默认关闭。需要临时落盘处理大事件时使用私有目录、明确生命周期并及时清理；只有显式启用记录才保留完整内容。后台归一化日志的既有保留行为单独说明。
5. CLI 版本探测按可执行文件身份缓存，提供刷新入口；过期缓存不影响启动，但显示其检测时间。网络 profile 诊断显示来源和是否设置，不显示变量值。

建议性能验收基线：受控夹具发出可展示事件后 500 ms 内出现反馈；原生进程启动前的 xcli 增量开销在固定环境下 p95 不超过 200 ms（版本缓存命中，不含安装/登录）；把总事件量从 100 MiB 扩大到 1 GiB，关闭完整输出记录时，峰值内存增量不应随总输出线性增长。先记录原始值和测量方法，再决定是否调整这些目标，不能当作当前成绩。

**七、MCP 与本地状态保护**

F02 修复需要同时设计迁移，不能把旧的部分指纹直接升级成“已确认完整”。区分两种比较：可编辑字段决定期望配置是否一致，完整原生条目决定 xcli 是否有资格执行覆盖或删除。规范化应保留值类型和数组顺序，消除键顺序、空白与注释差异。

写入流程建议为：展示计划 → 执行时获取 xcli 写锁 → 重读 ownership 与原生条目 → 验证计划仍适用 → 写入并读回验证 → 保存对应 ownership。不同 namespace 共用状态文件时，同样需要防止并发保存互相覆盖；多个目标加锁采用固定顺序。锁只能协调 xcli 实例，外部编辑仍依赖写入前重检和文件替换前的变化检测。

如果某个原生命令只能返回部分字段，不能声称已做完整保护；优先读取权威配置快照，无法取得时阻止不能证明安全的更新/删除，并说明限制。`--force` 仍遵循现有显式选择语义，显示受影响条目，不打印秘密值。

阶段 1 必须保证失败可见、外部字段保留以及旧状态的保守处理；阶段 4 再完善逐目标操作日志和中断恢复。发生“原生已写入但 ownership 未保存”时，下一次运行应报冲突/待恢复，不能误报全部同步成功；跨多个原生 CLI 不承诺全局原子事务。

`default` 等单字段配置修改复用 YAML 节点更新方式，保留注释、无关字段和权限。历史记录列表要报告损坏文件数量及可定位原因；失活任务依据进程所有权/锁证据整理，不能只凭时间或 PID 推断并发送信号。

**八、以三个场景完成用户流程**

| 场景 | 默认行为 | 交付结果 |
| --- | --- | --- |
| 日常任务 | 使用用户选择的 Agent，显示目录、活动与继续入口 | 最终回答、run ID、可用会话、验证是否执行 |
| 交叉审查 | 对用户选定的变更调用第二个 Agent；按原生能力施加只读权限 | 原始审查意见、文件位置、与测试证据的关联 |
| 实现与验证 | 在明确工作区实施，运行用户选定的本地验证命令，失败后进入有限修复 | diff、每轮验证证据、停止原因、人工接收路径 |

实现与验证的首版使用有限 DAG：实施 → 验证 → 失败时修复 → 再验证。新增显式条件依赖，保留现有 `depends_on` 成功依赖和 `continue_on_error` 语义；不同时引入任意循环、脚本表达式和自动调度。默认最多一次修复、显式总时限，每轮产物独立；耗尽后停止并交付失败证据。

只有用户声明为验证的 command 步骤能产生验证状态。验证结果绑定实际工作区内容摘要或快照引用：验证后再次改动则显示证据已过期。Agent 文本中的“测试通过”只能作为说明，不能生成 passed。

“继续原 session”“新开任务”“从失败步骤重跑”分开表达。从失败步骤重跑前校验工作区、配置和依赖产物；变更会使受影响步骤及其下游结果失效。不能无条件跳过之前成功但输入已经变化的步骤。

首版交付优先提供 worktree 路径、基线、完整 diff（包含已提交、未提交和未跟踪变更的说明）、测试记录与可复制的 Git 接收步骤。用户按指引手工提交和合并是可验收路径；自动应用改动作为可裁剪项。后续若增加自动接收，执行前预览目标分支、冲突与脏工作区，操作完成后保留来源与证据。模板本身不默认提交、合并或删除工作区。

工作区准备必须明确依赖安装、未跟踪文件、子模块与环境文件的处理。首版默认使用干净、已提交的基线；需要环境准备时由显式步骤执行，不自动复制密钥文件。只读审查能力不足的 Agent 要在启动前提示更换或选择明确的较弱模式，不能静默降级。

**九、文档、分发与价值验证**

将 README 快速开始压缩到发现工具、设置默认、完成任务、查看并继续四步；网络、MCP、ACP、后台任务、workflow 保留为场景专题。候选版示例注明最低版本，不能复制到稳定版说明中伪装成当前功能。

每次发布记录 xcli commit、原生 CLI 版本、OS/架构、run/JSON/resume/取消/MCP 的测试结果。真实调用需使用可用的测试账号与明确预算；未具备账号的组合标记未验证，不能用模拟事件通过代替端到端验证。安装归档需验证校验和、PATH 和版本号；Homebrew 仅在 tap 与安装链路实际就绪后列为官方可用方式。

发布工作流应依赖同一 tag 提交的模块检查、格式、vet、race、跨平台构建与打包检查，再执行正式发布。发布说明包含修复编号、受影响旧版本、状态迁移、行为变化、兼容矩阵与已知限制。

招募 10–15 位已使用多种 CLI 的开发者，观察首次任务、失败诊断、隔天继续以及可选的交叉审查。保持无默认遥测，使用自愿分享的本地诊断和访谈记录。初始实验目标：首次成功中位耗时不超过五分钟；有效七天观察样本中至少一半自发复用；受测恢复路径全部进入正确目录与 session。小样本用于决定下一轮投入，不用于声称市场留存率。

**十、决策规则**

目录错误、配置丢失、解析失败被报成功均阻断受影响能力发布；体验目标未达成则先修入门与恢复路径。多 Agent 对照没有稳定增益时，将其保持为可选场景。进度不足时依次裁剪自动接收、自动交互 session 捕获、短 ID/标题、更多模板和高级统计，保留可靠性、流式反馈、正确恢复与一个完整验证场景。

投入是否成功最终看用户能否独立完成并继续真实任务。对应的分阶段交付清单和每个里程碑的退出条件见[详细阶段计划](phased-roadmap.zh-CN.md)。
