**xcli 后续详细阶段计划 · 2026-09-08**

执行顺序为：冻结契约与复现基线 → 发布现有能力修复 → 打通日常使用 → 完成验证与交付 → 小范围试用及发布。优化依据与设计取舍见[优化方案](optimization-proposal.zh-CN.md)，缺陷编号沿用[审查报告](../reviews/2026-09-07-product-and-code-review.zh-CN.md)。

本文创建时所有任务均为“待开始”，没有将已有开发分支代码或历史测试结果视为本计划验收完成。2026-09-08 更新：阶段 0 的 A01–A03 已完成，交付与本轮证据见[阶段 0 验收记录](../phase0/results.zh-CN.md)；阶段 1–4 仍待开始。阶段 0 未包含生产代码修复、分支合并或发布动作。

**一、估算与版本策略**

暂按一名主要开发者、每周五个工作日估算，合计约 40–57 个工作日，即 8–12 周。相较审查中的 6–9 周粗估，这里额外计入契约冻结、旧状态迁移、独立试用与发布缓冲；工期仍是估算。开工日记为 T0，不绑定未经确认的日历日期。外部账号、发布基础设施或试用招募延迟可能增加日历时间。

| 阶段 | 工期 | 核心成果 | 里程碑与版本建议 |
| --- | --- | --- | --- |
| 0：准备 | 2 个工作日 | 复现样本、接口决策、依赖与支持范围 | M0：可以开始分模块实施 |
| 1：可靠性 | 8–10 个工作日 | F02–F07 公共修复；开发线 F01；发布门禁 | M1：稳定修复版，暂定 `v0.4.1` |
| 2：日常体验 | 10–15 个工作日 | 初始化、流式状态、任务摘要、正确继续 | M2：`v0.5.0` 候选版体验验收 |
| 3：验证与交付 | 15–20 个工作日 | 一个可运行的实现—验证—修复—交付场景 | M3：`v0.5.0` 功能候选版 |
| 4：试用与发布 | 5–10 个工作日，七天复用观察可跨周 | 实测兼容矩阵、问题收敛、安装与演示材料 | M4：满足门槛后发布 `v0.5.0` |

版本号是规划占位，开工时根据实际 tags 调整。只维护一条稳定线和下一版本开发线。公共修复从稳定基线分成小 PR，并同步到开发线；F01 随 worktree 代码处理，不把未发布功能引入补丁版。历史 `v0.1`—`v0.3` 保留问题说明与升级指引，不默认建立多条长期维护线。

现有 `origin/v.0.5.0` 是已审查的本地跟踪快照，包含可复用实现。按 worktree、command/plan、记录筛选、诊断、分发逐项核对后接入；避免把整个跨领域提交作为已经验收的发布单元。可以用临时集成分支重组提交，保留原有提交引用供追溯。

**二、任务责任与执行规则**

“开发负责人”负责代码、回归与文档，“验收负责人”复核用户场景和发布清单，“试用协调人”负责招募与记录；初期可由同一维护者承担，但真实试用由参与者独立操作。正式开始时为任务填写具体负责人，不能把本文的角色占位当作已经分派。

每项任务使用本文 ID，附复现或用户场景、变更范围、依赖、验收证据和兼容影响。建议状态为待开始、进行中、待验收、完成、阻塞；阻塞项写明下一步和解除条件。单人开发同时只保留一个主要实现任务，独立文档与用户反馈可穿插处理。

每个 PR 聚焦一个问题或一组不可拆分的契约变更；先完成有价值的定向回归，再运行相关模块和仓库必需检查。文档与无行为变化的低风险调整不额外堆积测试。阶段末按最终提交执行一次完整检查，代码改变或出现新失败才扩大复验。

2026-09-08 验收：**M0 已达到**。A01 [基线与缺陷归属](../phase0/baseline.zh-CN.md)、A02 [冻结契约](../phase0/contracts.zh-CN.md)、A03 [复现工具与验证矩阵](../phase0/validation.zh-CN.md)均已交付。两次模拟运行的 13 个适用案例均复现；真实 Codex 经额度恢复及用户追加两次调用授权后，普通 run/JSON → 同 session resume 验证已通过，包含上下文、实际 cwd 和记录关联。累计使用原预算 2 次及追加预算 2 次；其他真实兼容路径保留为发布前依赖，详情见[验收记录](../phase0/results.zh-CN.md)。

**六、阶段 3：验证、修复与结果交付，15–20 个工作日**

目标：利用现有 v0.5 command/plan/worktree 基础，交付无需手写 YAML 的一个完整场景。先保证单个可写步骤串行执行，再增加能力明确的交叉审查。

| ID | 工作内容 | 依赖 | 交付与验收 |
| --- | --- | --- | --- |
| D01 / 工作区整合 | 接入修复后的 worktree；规定干净基线、依赖准备、原仓库关联、步骤目录与清理生命周期 | B06、C04、C06 | plan 与实际 cwd 一致；源仓库状态符合预期；工作区丢失/基线改变明确报错；运行中不可清理，失败后保留可检查材料 |
| D02 / 验证证据 | 接入 command 步骤并显式标记验证角色；存储 argv/cwd/退出码/时间/产物和对应内容摘要 | B04、C02、D01 | 测试失败不会显示 passed；超时/缺证据为 inconclusive；验证后再修改使证据过期；敏感参数与完整输出遵循记录策略 |
| D03 / 有限失败分支 | 为 DAG 增加明确的失败条件依赖；定义恢复分支成功后如何合成 workflow 最终状态 | D02、A02 | 首轮验证失败可进入修复并重验；修复成功保留首轮失败证据；无恢复分支沿用旧行为；达到次数/时限停止 |
| D04 / 从失败点继续 | 区分新执行、原 session 恢复、步骤重跑；记录 attempt 与父记录；校验依赖快照与产物 | D03、C05 | 输入未变时复用有效步骤；输入改变使相关步骤及下游失效；不重复记账、不隐藏失败 attempts |
| D05 / diff 与接收路径 | 摘要展示工作区、基线、已提交/未提交/未跟踪改动与验证结果；提供人工 Git 接收指引 | D01、D02 | 用户知道修改在哪里并可接收；未跟踪文件不从摘要消失；不能把旧测试当成当前 diff 的证据；冲突有处理路径 |
| D06 / 三个场景入口 | 提供日常任务、交叉审查、实现与验证的模板/初始化入口；变量有说明和默认值 | C01、D03、D05 | 主场景不要求手写 YAML；模板标最低版本、目录、依赖和权限；只读适配失败在启动前显示；默认一个可写 Agent |
| D07 / 集成演练 | 前台与后台分别运行成功、验证失败后修复、最终失败、取消、恢复与清理场景 | D01–D06 | 记录/事件/退出码一致；后台等待超时不终止任务；原仓库不因错误 cwd 被修改；全部证据可定位 |

建议按 3–4 天完成 D01/D02、4–5 天完成 D03、3–4 天完成 D04/D05、5–7 天完成 D06/D07 安排。若状态机或适配权限耗时增加，先裁掉自动应用 diff 和更多修复轮次，保留手工接收路径及一次有界修复。

D03 首版采用“验证 → 条件修复 → 再验证”的有限节点，不引入任意循环。默认一次修复，总超时由模板明确给出。后续节点因条件不满足而跳过，与因依赖失败而跳过需要可区分；最终验证 passed 才能把已处理的验证失败视为恢复成功，启动失败/取消/产物缺失不能被无条件覆盖。

D02 的验证日志必须兼顾证据与隐私：默认保存命令的安全描述、状态、耗时与内容引用；完整日志只在显式启用后保留。修复步骤需要日志时使用受限的临时私有产物并清楚说明生命周期。候选模板若选择保留证据文件，入口必须明确展示该行为。

M3 的演示验收使用同一临时 Git 项目完成以下顺序：

1. 从声明基线建立 worktree，展示计划中的 Agent、cwd 和验证命令。
2. 实施一个能由本地测试检查的改动；先用确定性夹具覆盖调度，再用固定版本的真实 CLI 检查适配。
3. 让首次验证失败，失败日志传入修复步骤，再验证成功；独立保留每轮状态及耗时。
4. 展示真实 diff、验证证据及其关联的工作区内容，用户按指引接收改动。
5. 再演练修复耗尽、用户中断、工作区缺失，确认均停止并说明原因，不误报成功、不自动删除证据。

M3 退出条件：以上前后台路径均通过；三类场景入口可以运行；至少一个完整“实现与验证”场景无需手写 YAML；共享 worktree 的写入顺序和只读保护边界清楚。自动 Git 接收命令不作为首版硬门槛。

**七、阶段 4：试用、兼容与发布，5–10 个工作日**

目标：验证路线是否解决真实问题，补齐可安装、可解释、可维护的发布材料。七天复用观察从阶段 2/3 的可用候选版开始安排，不在发布当天一次性补做。

E02 的可选维护增强不能挤占关键缺陷修复。如果故障演练发现仍有配置丢失或误报成功风险，相关修复立即升级为发布阻断；通用自动恢复和新清理入口可后移，并保留可操作的手工恢复说明。

M4 产品判断：首次任务中位耗时目标 ≤ 5 分钟；完成完整七天观察的有效试用者中至少一半自发复用；受测恢复路径全部正确。分母、未完成观察、账号失败和异常样本都要记录。招募不足时延长观察，或保持带明确验证范围的候选版，不虚构结论。

工程门槛通过但产品目标未达成时，先处理被观察到的主要阻力；若多 Agent 缺少额外有效发现，则保持可选，不放到默认任务路径。小样本判断只指导下一阶段，不用于对外宣称稳定留存或市场规模。

必须保留：F01–F07 对应修复、旧状态兼容、结果真实性、实时活动、正确继续、一个完整验证场景、人工接收指引、发布提交检查。可延后：自动应用 diff、跨 Agent 自动摘要、交互 session 自动发现、任务标题/短 ID、多轮修复、更多模板、高级统计、新的日志清理入口。每次裁剪同步修改版本说明与演示，不能只减少测试范围。

**九、统一验证与发布清单**

| 验证层 | 关键场景 | 证据要求 |
| --- | --- | --- |
| 模块回归 | 完整指纹、深拷贝、解析、cwd、状态合成、旧数据读取 | 针对用户不变量的测试，缺陷修复前能失败、修复后通过 |
| 跨模块集成 | run/resume/workflow/后台同一错误；MCP 计划到写入间变化；取消、重试、恢复 | 隔离环境、实际退出码、记录和原生文件前后对照 |
| 性能与资源 | 流式首个反馈、缓存命中启动耗时、100 MiB/1 GiB 输出、慢消费者 | 固定硬件/版本、原始样本、p95 与峰值内存；目标变更有依据 |
| 原生兼容 | 四类 CLI 的固定版本关键路径，适用的 user/project MCP | 真实账号路径与模拟夹具分开；限制和未验证项可见 |
| 安装与发布 | macOS/Linux 归档、四个构建目标、校验和、PATH、版本、最小 run | 交叉构建不等于实机运行；列出实际执行过的平台组合 |
| 用户体验 | 首次任务、失败诊断、隔天恢复、检查并接收 | 用户独立操作记录与问题清单，避免维护者代操作掩盖阻力 |

代码发布必需检查沿用仓库现有基础并加强提交关联：`go mod tidy -diff`、Go 格式检查、`go vet ./...`、`go test -race ./...`、Darwin/Linux 的 amd64/arm64 构建、GoReleaser snapshot。发布流程需要等待这些检查在同一 tag commit 上通过，正式发布与 snapshot 分开执行。

每次里程碑发布前逐项核对：

- [ ] 修复编号与任务 ID 对应到已合并变更，公共修复已同步到开发线。
- [ ] JSON 默认行为、退出码、workflow cwd 与旧记录/旧 ownership 的兼容样例通过。
- [ ] 没有未解决的配置丢失、目录错误、错误状态覆盖或把未验证结果当成 passed 的路径。
- [ ] 原生版本/平台矩阵更新；不能确认的范围不写“已支持并验证”。
- [ ] 安装指令、版本号、release notes、示例最低版本和已知限制一致。
- [ ] 发布归档来自通过检查的最终提交，校验和可用。
- [ ] 用户数据迁移和降级限制有说明，失败后保留可定位的诊断与恢复路径。

回退原则：可执行文件回退与数据格式回退分开判断。新增可选 run 字段以兼容读取为主；MCP ownership schema 升级后，旧二进制可能无法理解，不能直接恢复旧指纹并继续写配置。保留迁移前的私有备份和恢复说明，恢复前核对原生配置现状。候选版回退优先停用新增能力、保留工作区与记录，不自动清理用户数据或覆盖配置。
