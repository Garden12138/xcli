## 假设与输入

原 Work/Project 对照中三种方法最终均通过，无法从通过率建立协作增益。本轮只增加一个预定义的合成 Work 场景 `release-evidence-v1`，检验独立 CLI 复核能否发现执行和自查遗漏的规则冲突。单次合成场景不代表真实用户工作或普遍质量提升。

固定输入为发布规则、目标列表、测试记录和审批记录四份材料；覆盖精确版本/摘要匹配、旧版本、撤销、未来记录、其他环境、截止时刻、到期时刻和依赖阻塞。目标是产出一致的 report.json 和 report.md，并用 CSV 记录 ID 与文件名支持每项发现。完整规则都在输入中，评分答案不进入 Agent 工作目录或反馈。

固定顺序为 Task 指定 Codex、直接 Codex、Task Codex 执行 / Cursor 复核。三组使用逐字相同的材料、相同的核心目标和完成标准、同一个生产候选、每组十分钟及最多五次分派；各组控制协议按产品实际路径运行。Codex reasoning effort 固定 low，模型沿用冻结时的原生默认值；原生版本、二进制、输入、工具和评分器摘要在真实调用前冻结。

直接组执行实现与一次自查/修正，通常两次分派；Task 组执行协调、worker 与 reviewer，通常三次，保留一次修复机会但不追加隐藏评分答案。报告实际投入，不把未用调用补齐以制造“相同成本”。总预算建议不超过 16 次，预计正常八次；旧补充预算的剩余两次不挪用。失败、取消及原生启动失败的分派仍计数。

## 评分及收益规则

- 独立检查每个目标的决定、版本、摘要、汇总、报告一致性、全部支持发现、遗漏和误报；无效记录 ID、缺失来源、重复/虚构发现均不通过。评分器只在完成后运行，不反馈给模型指导修复。
- Task 必须保持指定/自动模式和实际角色；跨 CLI 必须由 Codex 执行、Cursor 复核，且复核绑定当前产物摘要。原材料必须保持不变。
- 每个基线分别比较。只有基线实际正常完成、输入/角色/复核约束保持，且跨 CLI 独立验收通过时，才评价质量收益。登录、额度、流解析、进程或协调失败单独记录，不算质量收益。
- 记录“相对任一基线的改进”和“相对两个基线均有收益”两个指标。只有跨 CLI 相对直接组和单 CLI Task 组都提高独立验收结果或支持发现数，才声明本合成样本建立协作收益；否则不归因于换用第二个 CLI。
- 全部同样通过时明确记录无收益。不得用自动交接数量代替真实人工交接，不能从该实验推断减少用户求助或留存。耗时、分次用量和未知成本分别保留，不填零成本或声称更省。
