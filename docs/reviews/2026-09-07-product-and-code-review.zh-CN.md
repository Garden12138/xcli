**产品定位应继续聚焦用户已经认可的主张。** 初衷对话中，你明确认可的是“一个用于安装、运行、切换和编排主流 AI Coding Agent CLI 的统一入口”。代理分流、统一会话和更广泛的平台化能力是原对话进一步提出的建议，适合作为待验证假设，不能全部视为必须交付的范围。

当前架构符合主张：调用真实 CLI，复用原生认证、权限和高级参数；Go 单二进制降低运行依赖；配置与网络环境可以按 Agent 组织；工作流已经能串联多个执行过程。这个方向值得保留。

需要收敛的是对用户价值的表达。已安装 Claude 和 Codex 的用户，不会因为把两个启动命令换成两个更长的命令而长期留下。他们更可能为以下结果留下：无需重复修网络和 MCP；第二天能找到并继续上次任务；不同 Agent 能围绕同一个改动交接；能明确看到测试是否通过、改动在哪里、下一步怎么处理。

建议对外表达为：**“xcli：统一使用你的 AI 编程 CLI，让任务可追踪、可验证、可继续。”** 副文案再说明支持 Claude Code、Codex CLI、Gemini CLI、OpenCode，沿用原生登录与工具能力，并统一管理环境、MCP 和工作流。

F01 的实现原因是 `cmd/workflow.go` 仅映射 `prepared.WorkingDirectory`，步骤仍交给 `resolveDirectory(workflowCwd, step.Cwd)`，后者原样接受绝对路径。复现使用如下步骤，在干净临时仓库执行 `workflow run <file> --worktree --json`，最终原仓库出现 `escape-marker`，隔离目录没有该文件：

```yaml
version: 1
name: isolation-check
cwd: .
steps:
  - id: write
    command: /usr/bin/touch
    args: [escape-marker]
    cwd: /absolute/path/to/original/repo
```

建议在 Prepare 阶段解析全部步骤目录，将仓库内的绝对路径映射到隔离目录；对仓库外目录、`..` 越界和符号链接的最终位置给出明确处理。plan 与 run 应使用同一份解析结果。Git worktree 并非操作系统沙箱，这个修复针对的是 xcli 自身给步骤分配错误工作目录的问题。代码：[v0.5 workflow 命令](https://github.com/Garden12138/xcli/blob/6d59f7fa2b3e83a89e9450927b507320f44264f7/cmd/workflow.go#L186)、[步骤目录解析](https://github.com/Garden12138/xcli/blob/6d59f7fa2b3e83a89e9450927b507320f44264f7/internal/workflow/runner.go#L512)。

F02 的最小复现是：同步项目级 Claude HTTP MCP → 在生成条目上加入 `headers: {"X-Audit-Change": "added-after-sync"}` → 再次 plan → 从 xcli 源配置移除该 server → sync。两个分支均显示 noop，v0.5 还显示 `in_sync: true`，最终同步成功删除整个原生条目。解析器只把 transport/url 等字段放入 `Entry`，指纹没有覆盖新增的原生字段。建议保存完整原生条目的规范化指纹，执行前重新验证；未知厂商字段可以不提供编辑能力，但必须参与保护。代码：[原生条目解析](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/mcp/manager.go#L224)、[所有权和漂移判断](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/mcp/engine.go#L119)。

F03 的根因很直接：`cloneMCPServer` 把 `value.Env` 替换为空 map，再遍历这个空 map，所有键值都被丢掉。复现配置原有 `targets: [claude]` 和 `env: {LOG_LEVEL: info}`，从 Gemini 原生配置导入指向同一源的 xcli wrapper；结果 targets 正确变成 `[claude, gemini]`，env 被删除。修复应先保留原 map 再复制，并测试 import 扩大目标范围时的完整配置不变量。代码：[cloneMCPServer](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/mcp/import_engine.go#L231)。

F04 的根因是 `StepRecord` 未保存 cwd，`resumeTargetFromRecord` 初始化时直接使用 workflow 的 `record.Cwd`。复现中，模拟 Agent 原始执行输出为 `repo/sub`，恢复后输出为 `repo`。实际原生客户端也可能有自己的 cwd/session 约束，必须另外验证，但 xcli 已经传错了目录。代码：[恢复目标解析](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/cmd/resume.go#L189)、[步骤记录](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/runstore/store.go#L46)。

F05 的根因是 Scanner 上限为 4 MiB 且未检查 `scanner.Err()`；无效 JSON 行也被跳过，最后回退为最后一行文本。复现“session 开始事件 → 5 MiB 消息事件 → usage 事件”后，xcli 退出 0、status 为 success、output 变成最开始的 session JSON，usage 丢失。另一项 v0.5 复现是输出 `not-json` 且进程退出 0，也得到 success。应将进程退出状态与结果解析状态分开，检查完成事件和错误事件，给出 `parse_error` / `truncated` 等机器可读信号。同时改为增量解析和有界缓冲，避免先在内存里累计全部原生输出。代码：[解析器](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/agent/agent.go#L374)、[完整 stdout 缓冲](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/runtime/process.go#L39)、[结果状态覆盖](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/cmd/run_exec.go#L72)。

F06 涉及 `implement-and-review.yaml` 和 `parallel-review.yaml`：两者写 `cwd: .`，而引擎以 workflow 文件所在目录解析，所以 README 从仓库根运行它们时，实际目录为 `examples/`。v0.5 的新 `verified-workflow.yaml` 已正确使用 `cwd: ..`，应同步修正旧示例，并在计划和运行摘要中突出 cwd。不要直接改变引擎语义，以免破坏已有用户的文件。代码：[旧实现示例](../../examples/implement-and-review.yaml)、[旧并行示例](../../examples/parallel-review.yaml)、[解析基准](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/internal/workflow/runner.go#L110)。

F07 的原因是 doctor 的健康判断主要依赖 `Installed`；v0.5 的 deep 模式补充了 ACP 命令可用性，却没有把版本检测错误纳入健康状态，能力字段也主要来自适配器静态声明。建议输出“已声明支持 / 当前已检测可用 / 未验证”，按用户实际选用的路径判断健康，避免只使用普通 run 的人因为缺少可选 ACP bridge 而被误导。代码：[main doctor](https://github.com/Garden12138/xcli/blob/feae6070dfa63049cad51e9f37511650914618c3/cmd/agents_doctor.go#L72)、[v0.5 doctor](https://github.com/Garden12138/xcli/blob/6d59f7fa2b3e83a89e9450927b507320f44264f7/cmd/agents_doctor.go#L111)、[静态能力表](https://github.com/Garden12138/xcli/blob/6d59f7fa2b3e83a89e9450927b507320f44264f7/internal/agent/agent.go#L74)。

**用户体验需要围绕完整任务重新组织。** 当前快速开始把配置初始化、安装、认证、ACP、MCP、路由、后台任务、工作流和费用放在一条长路径上。用户还没有得到第一次成功，就先接触了大量内部概念。

建议将入门压缩为“发现已有 Agent → 选择默认工具 → 成功完成一个任务”，高级功能放到场景教程中。无需重新实现原生聊天界面，可以先做轻量交互选择和清晰摘要。

| 用户阶段 | 当前阻力 | 建议变化 | 可验证的体验目标 |
| --- | --- | --- | --- |
| 第一次了解 | 首屏以功能和协议为主 | 先展示一个具体任务及完成后的结果，再介绍架构 | 用户读完首屏能说明为什么使用 xcli |
| 安装 | 手动选归档、校验、复制、处理 PATH；v0.5 分发待落地 | 验证 Homebrew/Go/归档安装路径，检测 PATH 并给出对应修复命令 | 全新环境复制官方指令可成功执行 `xcli --version` |
| 初始化 | `config init` 固定设置 codex，不依据已有安装 | 引导用户从已安装且可用的工具选择；支持非交互显式配置 | 已有 Agent 用户无需安装第二个工具即可开始 |
| 执行中 | 内置结构化 stdout 在结束后才归一化输出 | 持续显示运行阶段、耗时、最近活动；提供 JSONL 事件 | 用户能区分正在工作、等待输入和异常退出 |
| 执行结束 | 普通 run 缺少醒目的 run ID 和继续入口 | stderr 显示 run ID、cwd、下一步；JSON 增加稳定 run ID | 不必先遍历历史就能继续刚才的任务 |
| 隔天继续 | 长 ID、多套 list/show；`use` 缺少 session ID | 最近任务、按项目筛选、短 ID/标题、`resume --last` | 能找回正确项目和会话，而非猜 ID |
| 工作流失败 | 依赖必须成功；失败输出不能自然送到修复步骤 | 显式失败分支、失败产物和从失败步骤恢复 | 测试失败可进入修复流程，不重跑已成功的昂贵步骤 |
| 接受结果 | worktree 保留下来，但用户还需自行整理 Git 操作 | 结果摘要、diff、测试证据、打开目录和明确的接收操作 | 用户知道修改在哪里、验证了什么、如何接收 |

这里的命令和行为都是建议，不是对当前实现的描述。可优先做 `xcli` 的轻量选择页、`resume --last`、`runs show --human`、任务摘要和统一 `status`；保留已有命令兼容性，用帮助分组减轻认知负担。

“切换”需要拆成三种用户理解：切换下次启动的默认 Agent、恢复同一个原生 Agent 的 session、把当前任务交给另一个 Agent。当前前两者只实现了部分连续路径，第三种尚无通用上下文交接。尤其 `xcli use codex` 创建的记录没有 session ID，复现后再 `resume <use-id>` 会得到 `has no recorded session id`。即使开启输出记录，当前 use 路径也不会自动解析 session。应在产品中明确可恢复能力，再通过原生会话索引或协议适配补齐；跨 Agent 交接应传递用户选定的任务摘要、文件差异和验证证据，不声称可以移植厂商私有 session。

工作流方面，现有 `continue_on_error` 只允许独立分支继续，依赖失败步骤的后续任务仍会跳过。建议保留默认失败即停，同时新增显式 `on_failure` 或条件依赖，配合受限重试次数、总时限和失败日志产物。重跑一个有文件写入的 Agent 步骤，可能产生重复修改，故需要区分“新开一次执行”“恢复原 session”“从保存的工作区重试”的语义。

建议提供三个内置场景，均允许用户明确选择 Agent：

- 日常任务：一个 Agent 执行，显示变更和验证结果；这是默认路径。
- 交叉审查：已有变更交给另一个 Agent，保留原始意见、文件位置和与验证结果的关系；不把多模型同意自动当成正确结论。
- 实现与验证：实施 → 本地测试 → 失败时修复 → 有界重验 → 人工检查，结果必须区分“进程结束”“测试通过”“改动被用户接受”。

只读审查不能仅靠 prompt 中的“不要修改文件”。应按适配器映射原生只读权限，并显示实际可提供的保护级别；不支持的适配器应明确说明能力不足，不能静默降级。这项能力对建立“放心交给多个工具检查”的信任很重要。

**竞争力应建立在可证明的完整体验上。** 重新核对了原对话涉及的项目，并增加原生产品能力作为替代方案。以下是官方仓库/文档声明的能力比较，没有实测它们的全部功能，也没有使用原对话中“相似度 95%”之类缺乏客观标准的评分。

| 对照对象 | 当前资料支持的能力 | 对 xcli 的含义 |
| --- | --- | --- |
| Forge | ACP 终端界面、统一历史、Agent 安装和模型/模式选择；文档也提示并非所有列出的 Agent 都已可运行 | 统一入口已有直接竞争；可以学习更短的上手路径。来源：[Forge](https://github.com/forge-agents/forge) |
| AWS CAO | 本地服务、隔离终端中的真实 CLI、supervisor/worker 协作、Web UI 和工作流 | xcli 的无常驻服务路径有简洁性优势；完整平台能力已有竞争。来源：[CAO](https://github.com/awslabs/cli-agent-orchestrator) |
| MCO（mco-org/mco） | 并行分发、review/run、实时/JSONL 输出、原始回答对比、原生权限 profile 映射 | review 不能只靠“两个 Agent 同时运行”形成差异。当前文档明确不管理 worktree，xcli 可把工作区、验证和结果接收连起来。来源：[MCO](https://github.com/mco-org/mco) |
| Maestro（josstei/maestro-orchestrate） | 跨 Gemini、Claude、Codex、Qwen 的工作流入口、持久会话和质量门槛 | 开发流程模板和 Agent 内调用也是竞争维度。来源：[Maestro](https://github.com/josstei/maestro-orchestrate) |
| 原生 Codex 工作区体验 | worktree、后台工作、在本地与 worktree 间交接、环境准备 | “支持 worktree”本身不足以形成吸引力；xcli 需要证明跨 CLI 的完整体验收益。来源：[官方 worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees) |

原对话将 MCO 描述为自动聚合、去重并提供结构化审查结论；当前 MCO README 更强调保留原始回答，并明确不把自然语言自动转成 findings、severity 或 consensus。因此不应沿用旧描述作为今天的产品决策依据。[MCO 当前说明](https://github.com/mco-org/mco)

建议建立三层竞争力：

1. 日常收益：切换工具时环境和网络正确，配置错误能诊断，已有原生配置能可靠复用。这决定用户是否愿意先装上。
2. 持续收益：所有任务有稳定身份、项目归属、可恢复路径和结果证据。这决定用户是否会反复使用。
3. 积累优势：真实 CLI 版本兼容矩阵、长期回归样本、经过验证的工作流模板、配置迁移保护和完整任务记录。这比增加几个包装命令更难复制。

中文文档、代理 profile、无常驻服务和本地记录可以形成有用的组合，但都不宜宣称独有。需要用任务成功率、操作次数、故障恢复时间等证据证明组合价值。

**吸引力和获客应围绕可见结果设计。** 当前 README 更像功能手册。建议首屏先回答“为什么已经有原生 CLI 还要装 xcli”，紧接一段 60–90 秒演示：发现本机工具 → 启动任务 → 查看实时进度 → 看到改动与测试 → 交给另一个工具复核或继续。演示应公开实际执行链路及失败情况，不预设多 Agent 一定更好。

更具体的材料建议：

- 一个最短入门页，只完成第一次任务；MCP、ACP、workflow 各自成为专题。
- 三份可直接运行的任务模板，变量有默认值，所需 Agent、目录、权限和本地依赖清楚可见。
- 一张“原生命令能做什么 / xcli 新增什么”的对照表，明确原生功能继续可用。
- 用同一个任务比较手工切换与 xcli 的操作步骤、诊断时间、结果整理时间；记录失败，不只录成功视频。
- 提供可供其他 Agent 调用的说明和稳定 JSON schema，让 Claude/Codex 等在需要时使用 xcli；先完成 CLI 契约，再判断是否需要额外暴露编排 MCP 服务。
- 添加贡献指南、适配器兼容性问题模板、版本测试结果和清晰 roadmap，让社区知道该反馈什么、怎样验证。

品牌名 `xcli` 可以保留，但应始终配具体描述，例如 “AI coding CLI manager”，降低名字本身过于泛化带来的理解成本。是否改名应依据搜索与用户辨识测试，不建议现在先投入品牌重做。

**工程优化应服务上述体验。** 当前模块边界总体合理，严格 YAML、argv 执行、MCP 的显式计划、后台锁校验、私有元数据和 race 测试都是值得保留的基础。没有必要为了架构整齐而整体重写。

建议按下面顺序补齐关键契约：

| 契约 | 具体变化 | 解决的问题 |
| --- | --- | --- |
| Agent 结果 | 按原生适配器分离事件解析；记录 CLI 版本、解析状态、原生错误与完成信号 | 降低通用启发式解析误判及升级漂移 |
| Run 身份 | 统一 run ID、parent/step、实际 cwd、原生 session、workspace、artifact、验证状态 | 让前台、后台、workflow 和 resume 能围绕同一任务工作 |
| 流式事件 | `started/progress/waiting/completed/failed` 等稳定事件，有界缓存，stdout/stderr 角色明确 | 同时改善人类使用和其他 Agent/CI 调用 |
| 工作区 | Prepare/plan/run 共用目录解析与映射；步骤 cwd 入记录；恢复和清理状态一致 | 修复隔离和连续性缺口 |
| MCP 所有权 | 完整条目指纹、执行前重检、状态写入与原生写入失败恢复、串行化同一目标写入 | 避免丢失外部配置，减少半同步状态 |
| 兼容性 | 记录脱敏的真实 CLI 版本样本；稳定版/候选版矩阵；按平台做 smoke test | 让“支持四种 CLI”成为可验证承诺 |

另外几项可较小成本改善维护性和可靠性的事项：

- `config.Save` 整体 marshal YAML，而 `default` 会调用它，导致注释丢失并展开内置默认配置。可复用 MCP import 的 YAML 节点补丁方法，仅修改目标字段。
- `use/run/resume` 在 v0.5 加入同步版本探测，单次最长五秒。可缓存版本并有明确刷新入口，避免启动时每次付出额外延迟。
- 运行记录和 worktree 元数据的 List 会跳过损坏文件。可增加诊断计数，避免用户看到“历史少了”却不知道原因。
- 普通前台任务、ACP、后台任务的生命周期持久化程度不同。对前台异常中止后的遗留 `running` 状态，需要明确恢复和清理方式；worktree 的管理不应永久卡在失活记录上。
- 日志保留应提供明确配置及预览清理入口。保留当前默认不记录完整输出的选择，同时说明后台归一化日志和交互/ACP 用量统计的范围。
- 当前 release workflow 在 tag 推送时直接发布，文件内没有先运行完整检查。建议发布复用验证流程，保证发布的同一提交通过测试、构建和打包检查。
- v0.5 的 46 文件单提交横跨多个领域，不利于回归定位。后续按修复、工作区、验证、诊断、分发拆分可审查变更。

暂不建议仅为提高覆盖率而增加大量实现镜像测试。优先补本文复现涉及的跨模块不变量，以及原生版本升级、取消/恢复、部分配置写入失败等用户路径。

**建议以三个可验收的阶段推进，时间是单人开发的粗估，不是承诺。** 公共缺陷可以先作为 main 的修复版本处理，再同步到 v0.5；不要为了发布新能力而把公共可靠性问题继续带下去。

| 阶段 | 目标 | 核心交付 | 完成标准 |
| --- | --- | --- | --- |
| 第一阶段，约 1–2 周 | 可以信任现有能力 | F01–F07；目录与 MCP 回归；解析状态；验证安装和发布路径 | 全部最小复现转为有效回归且通过；四类 CLI 的关键 smoke 路径有版本记录 |
| 第二阶段，约 2–3 周 | 可以顺畅地每天使用 | 轻量初始化、实时进度、run ID/结果摘要、最近任务/按项目继续、README 场景化 | 已有 CLI 用户能独立完成首次任务，并正确找回上次任务 |
| 第三阶段，约 3–4 周 | 有值得留下的工作流 | 内置实现与验证、失败分支、证据产物、worktree diff/接收路径、交叉审查 | 测试失败能进入有界修复；用户能检查证据并决定接收；无需手写 YAML 完成主场景 |

每阶段结束都应依据真实试用调整下一阶段。TUI 全量重做、Web 控制台、远端集群、通用插件 SDK、大规模扩充 Agent、预测“最聪明路由”和统一账单平台，现阶段都可以暂缓。尤其不要把“支持更多 CLI”当成改善现有四类工具兼容性的替代指标。

**验证产品方向的方法。** 建议先招募 10–15 位已使用两种以上 CLI 的开发者，观察其完成真实任务，而不是只询问是否喜欢设想。至少包含 macOS/Linux 用户和需要网络 profile 的用户。每位用户观察一次安装/初始化、一次失败诊断、一次隔天恢复；再让其中有需求的人尝试第二 Agent 审查。

| 假设 | 建议观察指标 | 初始实验目标，非现有成绩 |
| --- | --- | --- |
| 上手足够简单 | 已有 CLI 用户首次成功任务耗时与求助次数 | 中位数不超过五分钟；不需要维护者代改配置 |
| 有日常价值 | 七天内自发再次使用 | 10–15 位试用者中至少一半主动重复使用，记录具体用途 |
| 会话管理有效 | 找回任务并在正确目录继续的成功率 | 受测路径均恢复到正确项目和 session |
| 多 Agent 有增益 | 新发现被用户接受的问题、误报、额外耗时/token | 与单 Agent 对照；没有明显增益则不设为默认 |
| 网络/MCP 是痛点 | 导入成功率、unsupported 原因、诊断耗时 | 能解释并修复大部分首批真实样本，而非只通过示例 |
| 结果交付可信 | 用户看到实际测试证据并接收改动的比例 | 明确区分“执行成功”和“被接受的验证结果” |

可以先通过用户自愿提交的本地诊断、匿名统计和访谈记录收集这些信息，沿用无默认遥测的产品取向。早期样本只能帮助发现问题和比较方案，不能据此推断整个市场。

付费也应作为后续假设：个人核心流程保持开源，以兼容性和口碑积累用户；若团队开始重复提出共享模板、运行审计、集中策略或远端执行，再验证相应付费需求。当前代码与公开材料不足以判断用户是否愿意为这些能力付费。

建议下一轮迭代只承诺一个具体成果：**一个已经安装主流 CLI 的开发者，可以在五分钟内通过 xcli 开始工作，随时知道任务状态，结束后检查改动和验证结果，并能从正确位置继续。** 这个成果会同时强化原有定位、首次吸引力、日常留存和后续编排能力的可信度。
